- **[AI (via Adam)]** Fixed a real DLL race exposed by `--workers 3` on the school computer: the first `[WinError 1114] c10.dll` failure (08-22, earlier today) looked like a one-off environmental fluke, but a `--workers 3` pilot run hit it in 3/20 videos (15%) — clearly not random. - **[AI (via Adam)]** The lock-based Whisper fix above was NOT sufficient -- re-tested at `--workers 8` on the actual server (Dell PowerEdge R740, dual Xeon Gold 6240R, 96 threads, 1.5TB RAM -- discovered this run is on the same class of machine `compute_scaling.md` described for training) and the c10.dll failure rate rose to ~25-35%, scaling *with* thread count despite the import already being serialized behind `_whisper_lock`. That rules out a simple import race. Real cause (Windows-specific, well documented): native DLLs using thread-local storage -- torch's C10/MKL among them -- must have Windows retroactively initialize TLS for every thread already alive in the process at `LoadLibrary` time, with a hard limit; loading torch for the first time while N worker threads already exist can fail from thread *count* alone. Fix: `preload_whisper()` now loads the model once in `main()`, single-threaded, before the `ThreadPoolExecutor` is created, so torch's DLLs are already resident before any worker thread exists. `transcribe_with_whisper()` simplified to just the inference call under the lock. Verified locally that the preload log line now appears before any per-video processing starts and normal operation is unaffected; the Windows TLS race itself can't be reproduced on macOS, so this still needs confirmation at `--workers 8`+ on the real server. (Files: `02_Data/collect_and_extract.py`, `02_Data/README.md`)
