- **[AI (via Adam)]** Fixed a real DLL race exposed by `--workers 3` on the school computer: the first `[WinError 1114] c10.dll` failure (08-22, earlier today) looked like a one-off environmental fluke, but a `--workers 3` pilot run hit it in 3/20 videos (15%) — clearly not random. Root cause: `transcribe_with_whisper()`'s `import whisper` statement (which triggers torch's native DLL loading) sat outside `_whisper_lock`, so concurrent threads' first Whisper call could race on Windows' DLL loader simultaneously. Fixed by moving the import inside the lock, serializing the whole first-import-and-load sequence across threads. Re-verified no regression/deadlock on a real 2-video concurrent run on this machine before shipping (can't reproduce the Windows-specific race itself locally, but confirmed the fix doesn't break normal operation). (Files: `02_Data/collect_and_extract.py`, `02_Data/README.md`)

- **[AI (via Adam)]** The lock-based Whisper fix above was NOT sufficient -- re-tested at `--workers 8` on the actual server (Dell PowerEdge R740, dual Xeon Gold 6240R, 96 threads, 1.5TB RAM -- discovered this run is on the same class of machine `compute_scaling.md` described for training) and the c10.dll failure rate rose to ~25-35%, scaling *with* thread count despite the import already being serialized behind `_whisper_lock`. That rules out a simple import race. Real cause (Windows-specific, well documented): native DLLs using thread-local storage -- torch's C10/MKL among them -- must have Windows retroactively initialize TLS for every thread already alive in the process at `LoadLibrary` time, with a hard limit; loading torch for the first time while N worker threads already exist can fail from thread *count* alone. Fix: `preload_whisper()` now loads the model once in `main()`, single-threaded, before the `ThreadPoolExecutor` is created, so torch's DLLs are already resident before any worker thread exists. `transcribe_with_whisper()` simplified to just the inference call under the lock. Verified locally that the preload log line now appears before any per-video processing starts and normal operation is unaffected; the Windows TLS race itself can't be reproduced on macOS, so this still needs confirmation at `--workers 8`+ on the real server. (Files: `02_Data/collect_and_extract.py`, `02_Data/README.md`)

### 2026-08-26

- **[Emmanuel]** Built `compute_labels_v2.py`, a revised label computation superseding `compute_labels.py` (v1), after review of commit cd569ee found two statistical flaws in the v1 label (both confirmed by independent review): (1) views-per-day-since-upload assumes linear view accumulation, but YouTube views are front-loaded — the score decays with video age, so the label partly encodes "how new is this video" and age-correlated metadata features could predict it without learning content; (2) normalizing by CURRENT subscriber count is post-outcome (reverse causality: a viral video grows its own denominator), subs is also one of the 12 metadata model features (same post-outcome number in label denominator and model input = target-leakage shortcut), and v1's subs=1 fallback for hidden counts near-deterministically mislabeled those videos as viral. Also corrected a citation error found during the review: Wu et al. (2018)'s "relative engagement" is rank-percentile of average WATCH PERCENTAGE calibrated against video DURATION at a fixed 30-day horizon — v1's formula was never that metric and must not be cited as "following Wu et al."; v2 borrows only the rank-within-strata calibration method ("inspired by"). v2 design — stratify instead of divide: `log(1+views)` ranked within (category × age-band × channel-size-band) cells, top quartile = viral, equal-count quantile bands (default 4×4) per category, subs used only as a coarse stratifier (post-viral sub growth only mislabels if the channel crossed a band boundary — rare and disclosable — vs. continuously rescaling every score); every cell has ~25% positives by construction, so category/age/channel-size are marginally uninformative about the label (leakage shortcut removed by design) and the proposal's own "similarly sized channels, same category" definition is implemented literally. Degenerate inputs are excluded and recorded in `labels_excluded.csv` (videos <30 days old at collection, missing dates/view counts, hidden/missing subs), never imputed. Verified on a 400-video synthetic cohort with planted confounds (views correlated with both subs and age) and all exclusion cases: viral rate flat at ~27–28% across every age and size band (vs. 0%→81% across size bands for a naive raw-views quartile — the exact artifact stratification removes), all 11 exclusions caught with reasons, byte-identical output across runs. A `fetch_channel_stats.py` draft (channel-median-views normalizer) was created and deleted the same session — the channel-median approach was rejected in discussion because snapshot data cannot give the channel's PRIOR uploads at the SAME view-horizon (it would mix future uploads and unequal accumulation windows). **Pending Adam's sign-off, since this revises the label definition locked in CLAUDE.md** — v1 kept as reference until then; CLAUDE.md's label wording deliberately NOT updated yet.
