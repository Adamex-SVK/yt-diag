# 02_Data — README

## Purpose
Dataset documentation, YouTube API data collection, preprocessing pipelines, and exploratory data analysis (EDA).

## Data source

**YouTube Data API v3** — 4 categories, 2,000 videos each, 8,000 total (locked ticket #3, 2026-08-20):
- Comedy/skits (categoryId=23)
- Tutorials & how-to (categoryId=26)
- Vlogs (categoryId=22 + `q=vlog` workaround)
- Product reviews (categoryId=24, Entertainment, + `q=product review` workaround — locked ticket #4, 2026-08-20)

## Per-video features

| Signal | Format | Encoder |
|--------|--------|---------|
| 12 metadata features | Structured (duration, publish hour/day, tag count, title/desc length, category, channel subs/age) | Raw → baseline models |
| Thumbnail | 1280×720 JPG | Pretrained vision backbone (DINOv2 ViT-S/14, frozen) |
| 20 frames (16–24 range) | **Not uniform** — 60% of frames densely sampled in the first 60s, remaining 40% spread across the rest (locked in the Architecture Digest: engagement signal concentrates early) | Same DINOv2 backbone + attention-pool temporal aggregator |
| Transcript | YouTube auto-captions (~70-80% coverage) + Whisper fallback | Pretrained text transformer (ModernBERT-base, frozen) |
| Title + description | Text | Same ModernBERT-base |
| Visual engineered features | Color temperature (CCT), brightness/saturation/contrast, face presence/count/area/centrality — thumbnail + per-frame, mean/std across frames | Structured columns → metadata baseline; optional 4th projected modality into the fusion head |
| Audio/prosodic engineered features | eGeMAPS (88-feature openSMILE set: pitch, loudness, spectral, voicing) + explicit pause count/ratio/length via VAD | Same as above |

Architecture (frozen encoders, late-fusion MLP, Integrated Gradients attribution) locked in the "YT-Diag Architecture Digest" artifact, 2026-08-14. Engineered-feature scope from `01_Research/2026-08-14_scaling_and_features/additional_features.md`.

**Label**: views/likes/comments used ONLY for label construction (never model input).

## Notes
- Actual data files (CSV, frames, transcripts) go in the GitHub repo (`02_Data/processed/`, via Git LFS as of 2026-08-28), not here.
- CC-license constraint on frame/video download was explicitly dropped by team decision (see `cc_availability_scan_findings.md` addendum) — accepted as outside YouTube TOS for the download step specifically.
- YouTube API quota: `collect_and_extract.py`'s discovery step uses `search.list` (100/day free bucket); metadata/thumbnail/captions/video come from `yt-dlp` and don't touch official-API quota at all.
- `collect_and_extract.py` requires `ffmpeg` + `ffprobe` on PATH in addition to `yt-dlp`, plus `pip install -r requirements.txt` for the feature-extraction deps (numpy, opencv-python-headless, opensmile, webrtcvad) — set this up on any new machine (e.g. the school computer) before running it. `02_Data/processed/` is the dataset itself (tracked in git via Git LFS as of 2026-08-28); `collection_manifest.csv` and `collection_log.txt` are run logs, gitignored, not the dataset.
- **opencv packaging pitfall (found 2026-08-18, fixed):** `opencv-python-headless>=5` silently ships without `CascadeClassifier`, breaking the face-detection fallback. Pinned to `<5` in `requirements.txt`. Also: never have more than one of `opencv-python`/`opencv-python-headless`/`opencv-contrib-python` installed at once — they share the same `cv2` package directory and uninstalling one corrupts the others (`cv2.__version__`/`cv2.data` disappear). If this happens, `pip uninstall` all opencv variants and reinstall clean.
- **mediapipe pitfall (found 2026-08-18, not fixed, not needed):** `mediapipe==1.0.1` (current PyPI release) removed the `solutions.face_detection` API `collect_and_extract.py` was written against, and pulls in a conflicting `opencv-contrib-python` build as a dependency. Left out of `requirements.txt` entirely — `_face_detector()` in the script catches this and falls back to the OpenCV Haar cascade automatically (the sanctioned fallback per `additional_features.md` 1.3), so no functionality is lost, just some accuracy on small/angled faces.
- `download_video()` must request `bestvideo+bestaudio` (not `bestvideo` alone) — video-only streams have no audio track to extract eGeMAPS/prosody features from.
- **yt-dlp version pitfall (found 2026-08-20, fixed):** `yt-dlp<2026.08.19` fails every video download against YouTube's current anti-bot JS challenge (`HTTP Error 403`). Fixed by pinning `yt-dlp==2026.8.19` in `requirements.txt`, installing `deno` on PATH (`brew install deno` — now a hard requirement, checked by `check_dependencies()`), and passing `--remote-components ejs:github` on every yt-dlp call (`YT_DLP_EXTRA_ARGS` in the script). This is a moving target on YouTube's side — if downloads start failing again on the school computer, `pip install --upgrade yt-dlp` first before debugging anything else.
- **Whisper is English-only (`small.en`)**: discovery sets `relevanceLanguage=en` on `search.list` (found 2026-08-20 — a Korean-language test video had no English auto-captions and Whisper produced a garbage transcript). **Update 2026-08-27: `relevanceLanguage` is only a ranking hint and it is NOT a small fraction** — the prospective tracker's language backfill showed only ~39% of its cohort declared an English audio language (Hindi 29%). The tracker now gates admission on `default_audio_language`/`default_language` starting with `en`; the retrospective collection used the same discovery parameters, so its contamination must be measured (`backfill_published_at.py` now records both language fields into `metadata_extra.json`) and filtered post-hoc via `meta__language` before training.
- All three scripts (frame sampling, engineered features, label computation) were verified together on a real 2-video test batch (`jNQXAC9IVRw`, `9bZkp7q19f0`) end-to-end on 2026-08-20 before being called done — not just unit-tested in isolation.
- **Category-mapping quirk spread further (found 2026-08-22):** the bare-`videoCategoryId`-returns-0 quirk (previously only categoryId 22/24) now also hits comedy(23) and howto(26) — confirmed directly against the live API. All four categories now carry a keyword (`comedy`, `tutorial`, `vlog`, `product review`).
- **Windows encoding pitfall (found 2026-08-22, fixed):** every `open(..., "w")` in the script now passes `encoding="utf-8"` explicitly. Without it, Python on Windows defaults to the system codepage (cp1252) for text writes, which crashes (`'charmap' codec can't encode character...`) the instant a video's title/description/transcript contains a non-Latin-1 character (hit this on a real school-computer run — Arabic text in one video, an ₹ symbol in another). macOS/Linux default to UTF-8, which is why this didn't surface in local testing.
- **Chrome cookie pitfalls on Windows (found 2026-08-22):** `--cookies-from-browser chrome` fails two different ways — "Could not copy Chrome cookie database" if Chrome is still running (even in the background/system tray), and "Failed to decrypt with DPAPI" (yt-dlp issue #10927) against current Chrome's App-Bound Encryption, which has no clean fix for external tools. Added a `--cookies PATH` flag as the reliable alternative: export a Netscape-format `cookies.txt` via a browser extension (e.g. "Get cookies.txt LOCALLY") instead — that goes through Chrome's own extension API, not external DB decryption, so it isn't affected by either issue.
- **Single-threaded was far too slow for 8,000 videos (found 2026-08-22):** a real school-computer run averaged ~50s/video, which extrapolates to ~5 days for the full run. Added `--workers` (default 3, `ThreadPoolExecutor`) to process videos concurrently, with submissions staggered by `--pacing/--workers` so `workers` requests don't all fire in one burst (the exact pattern that triggered the bot-check above). Whisper inference is still serialized behind a lock (`_whisper_lock`) — one shared model instance, since loading a `small.en` copy per worker would cost too much RAM — so concurrency mainly overlaps downloads/frame-extraction/visual-features across videos, not Whisper transcription itself. Verified correct (no output corruption, genuine overlap, not just interleaved logging) on a real 3-video concurrent run before shipping.
- **Concurrency exposed a real DLL race, two attempts to fix it (found 2026-08-22):** with `--workers 3` on the school computer, `[WinError 1114] DLL-Initialisierungsroutine ist fehlgeschlagen` on `torch\lib\c10.dll` recurred in ~15% of videos — not the rare one-off it looked like single-threaded. First attempt: moved `import whisper` inside `_whisper_lock` (it previously sat outside, so concurrent threads' first import could race). This did NOT fix it — re-tested at `--workers 8` on a 96-thread server and the failure rate rose to ~25-35%, scaling *with* thread count despite the import being serialized. That pattern doesn't fit a simple import race; it fits a documented Windows-specific issue where native DLLs using thread-local storage (torch's C10/MKL among them) must have their TLS retroactively initialized for every thread already alive in the process at `LoadLibrary` time, with a hard limit — so loading torch's DLL for the first time while N worker threads already exist can fail from thread *count* alone, independent of import serialization. `preload_whisper()` now loads the model once in `main()`, single-threaded, *before* the `ThreadPoolExecutor` is created — this fix is real and still needed, but see below: it was not the dominant cause of the failure on this specific machine.
- **c10.dll's actual root cause (found 2026-08-22): AVX2 not exposed on this machine/VM, not a DLL/TLS race.** `Dependencies.exe -chain` on `torch/lib/c10.dll` found zero genuinely missing dependencies (only optional-Windows-component noise 12+ levels deep, unrelated to torch) — and `import torch` failed identically with *zero* worker threads, ruling out both "missing DLL" and "thread race" as the mechanism. `WinError 1114` is DLL-init-failed (the DLL loads, `DllMain` crashes), not "module not found". Direct CPU-feature check (`IsProcessorFeaturePresent`, `PF_AVX2_INSTRUCTIONS_AVAILABLE`) confirmed AVX2 is not available on this hardware/VM. torch ≥~2.0's default CPU kernels hard-require AVX2 with no fallback. **Fix:** pinned `torch==1.13.1` in `requirements.txt` (MKL with an SSE fallback path, no AVX2 requirement), which forced `numpy<2` (torch 1.13.1 is not numpy-2.x-ABI-compatible — confirmed via `RuntimeError: Numpy is not available`, not just a resolver warning) and an explicit `packaging` dependency (torch's version-comparison code needs it; not declared as a torch dependency, and this venv's setuptools no longer ships the `pkg_resources` fallback). Also swapped `webrtcvad` → `webrtcvad-wheels` (the real package has no Windows wheel and needs MSVC Build Tools, not present on this machine; the fork ships precompiled wheels and is a drop-in `import webrtcvad`). **Verified**, not just "torch imports": a real 100-video (`--target 25 --workers 8 --resume`) batch completed 26 videos with full audio/visual/transcript features and zero `WinError 1114` failures, spanning 3 categories — the exact concurrency load that previously failed 15-35% of videos. If that other machine's CPU/VM does expose AVX2, a newer torch + `numpy>=2` pin can likely be restored there — don't assume it without re-verifying (`IsProcessorFeaturePresent` check first, cheap and fast).
- **Two environment potholes on this shared Windows machine (found 2026-08-22), unrelated to the pipeline itself but block installing/running it:** (a) the global `pip.ini` (auto-generated by an NVIDIA tool for a different account, `go73jec`) has a malformed multi-line `extra-index-url`/`trusted-host` that breaks every `pip install` with `getaddrinfo failed` even though the network itself is fine — work around per-command with `PIP_EXTRA_INDEX_URL=""` / `PIP_TRUSTED_HOST=""` / `PIP_INDEX_URL=https://pypi.org/simple` env vars (env vars outrank the config file); separately, this network has no route to `download.pytorch.org` specifically, but plain PyPI works. (b) running the script from git-bash needs `.venv/Scripts` prepended to `PATH` in POSIX form (`/c/Users/.../Scripts`, not `C:/Users/...`) — the Windows-style form silently breaks bash's colon-delimited `PATH` parsing (the leading `C:` reads as its own empty entry) and manifests as `check_dependencies()` reporting yt-dlp/ffmpeg as missing even when they're installed.
- **The real 8,000-video collection run (2026-08-22 through 2026-08-25):** launched with the AVX2/torch fix plus a Whisper concurrency pool (see CHANGELOG.md 2026-08-23) on the shared Windows server above. Discovery came back far short of the 8,000 target — `search.list` pagination caps out well under 1,000 real results per category/keyword combination regardless of `totalResults` estimates, the same problem `cc_availability_scan_findings.md` already documented for the CC-filtered search. An overnight run also collapsed ~11.5h in when the `cookies.txt` session died and the script had no way to distinguish "this video is gone" from "our session got cut off" — burned ~1,100 videos as fake failures before anyone noticed; fixed with auth-break detection (6 consecutive auth-signature failures aborts the run instead of burning the queue) and fresh cookies. **Final real yield: 1,860 videos** (comedy 464, howto 373, vlogs 541, product_reviews 482) — short of 8,000 but a real, clean, fully-processed dataset, now committed to git via Git LFS (2026-08-28, ~3.9GB). Revisit expanding toward 8,000 via date-partitioned (`publishedAfter`/`publishedBefore`) discovery slicing if needed — not yet built.
- **macOS launchd + `~/Documents` pitfall (found 2026-08-27, fixed by relocation):** a launchd agent running `track_new_videos.py` from `~/Documents/GitHub/yt-diag` failed every tick with `can't open file ... [Errno 1] Operation not permitted` — macOS privacy (TCC) blocks background processes from `~/Documents`, `~/Desktop`, and `~/Downloads`, and Terminal's own access doesn't carry over. Granting Full Disk Access to Xcode's Python (`python3.9` binary, then its `Python.app` bundle) did **not** fix it after two attempts. Fix that worked: move the repo out of the protected folders (now `~/GitHub/yt-diag`) and repoint the agents — no permissions involved, immune to Xcode updates. Rule: **never host the tracker under Documents/Desktop/Downloads on macOS.**
- **Search quota day = midnight Pacific = 09:00 CEST (found 2026-08-27):** the 08:00 CEST discovery tick shares a quota day with anything run after 09:00 CEST the *previous* day. Five experimental discovery runs on 2026-08-26 exhausted the search budget, and the next morning's 08:00 tick hit `HTTP 429` on its last 8 search calls. The tracker handled it correctly (checkpoint frozen, window re-covered by the next discovery run), but the fix is scheduling: **the discovery tick now runs at 09:05 CEST — the first run of the fresh quota day — so manual runs later in the day can never starve it; the snapshot-only tick runs at 21:05 with `--no-discover`, and any manual tick should use `--no-discover` too** (a manual discovery run only risks its own 429s, never the scheduled one).
